## 1. 系統願景與核心架構（修訂）

MIIS Broadcast 旨在 VR 環境下達成亞秒級 AI 賽事播報。系統確立「視覺感知、後端快慢雙軌調度」架構：

```
LiveCCCameraWorker
  │  每 2 秒推論一次，輸出自然語言描述
  │
  ▼
[快軌 Fast Path] ─── 關鍵字掃描 ──────────────────► 若 P1: 立即 interrupt_tts()
  │                                                     + 觸發 MatchTracker 計分
  │
  ▼
[慢軌 Smart Path]
  │  完整語句 → GeminiWorker（帶 MatchTracker + RAG）
  │
  ▼
Gemini 串流生成 P1~P5 口播稿
  │
  ▼
OpenAI TTS（優先級播放）
```

**架構核心原則（三條不能妥協）：**
1. 比分數值由 Python `MatchTracker` 維護，絕不交給 LLM 計算
2. P1 事件不能因 Gemini 忙碌而被丟棄（現有 `_busy` flag 是 Bug，必須修）
3. 快軌不等待 Gemini 回應，直接決定 TTS 中斷

## 2. 快軌 (Fast Path)：可行設計修訂

### 2.1 設計澄清——不是「字元流」而是「段落級搶先掃描」

原始文件描述「字元流毫秒級掃描」。**實際上在現有架構中不可行**，原因：
- `live_cc_from_frames()` generator 只在整個 segment 生成完畢後才 yield
- Token 在 `model.generate()` 內部流動，沒有對外 emit 的鉤子

**可行且等效的方案（段落級快軌）：**
```
LiveCCCameraWorker.signal_segment 發出原始文字
  │
  ▼ [GUI thread：on_segment_received()]
  立即掃描 raw_text（LiveCC 完成 = Gemini 尚未開始）
  │
  ├─ P1 關鍵字命中 → [全線清除] + 排入 Gemini（計分延遲到 Gemini 確認後）
  │                   └─ 1. interrupt_tts()（清 TTS 文字佇列 + 音訊佇列）
  │                      2. gemini_worker.flush_and_abort()（直接呼叫，非 Signal）
  │                      3. gemini_worker.process_segment(...)
  │
  ├─ P2 關鍵字命中 → Gemini 任務插到 deque 最前端（不清除舊任務，不中斷 TTS）
  └─ 其他 → Gemini 任務附加到 deque 尾端
```

這在「LiveCC 生成完 ↔ Gemini 開始前」的間隙完成掃描，實際延遲 <5ms，對播報時序完全足夠。

### 2.2 關鍵字優先級表

| 優先權 | 觸發關鍵字 | 後端動作 |
|---|---|---|
| **P1** | `score, goal, foul, shot, basket, 進球, 得分, 犯規, 投籃` | 全線清除（TTS 佇列 + Gemini 佇列 + 中止當前 stream）→ 立即處理 → **Gemini 回傳 P1 後**才由 MatchTracker 計分 |
| **P2** | `pass, timeout, intercept, block, 傳球, 暫停, 抄截, 封蓋` | Gemini 任務插到 deque 最前端（不清除舊任務，不中斷 TTS） |
| **P3** | 其他描述 | 正常附加到 deque 尾端 |

**P1「全線清除」的核心邏輯**：P1 代表場上出現了一個關鍵轉折點。此時間點之前排隊的所有描述都是舊世界資訊，播出去只會讓觀眾困惑。清得越乾淨，P1 播報越快，高潮同步感越強。

**計分在 Gemini 確認後才觸發的原因**：快軌掃描只知道「有得分關鍵字」，但不知道是哪隊、是真實得分還是進攻失敗的描述（如 "attempts a shot"）。由 Gemini 分析完整語意後，在 `signal_broadcast` 回傳 `action_label == "score"` 時才呼叫 `MatchTracker.add_score(team)`，可避免 LiveCC 幻覺或模糊描述造成的計分錯誤。

P2 不清除的原因：賽事節奏轉折（換人、暫停）屬於「連續情境」，前一句話的脈絡還有用，插隊但不清除舊內容。

### 2.3 實作位置

快軌掃描邏輯寫在 `gui.py` 的 `on_segment_received()` handler（連接 `signal_segment`），**不要寫成獨立 worker**，避免增加不必要的執行緒開銷。

## 3. 關鍵 Bug 修復：GeminiWorker `_busy` flag

### 3.1 問題

`workers/gemini.py:62-63`：
```python
if self._busy:
    logging.debug("[GeminiWorker] Busy, dropping segment %.2f-%.2f", start_t, stop_t)
    return
```

**當 Gemini 正在處理 P3 日常描述時，進球事件的 P1 segment 直接被丟棄。** 這讓整個優先級系統形同虛設。

### 3.2 解決方案：deque 佇列 + 跨執行緒中止旗標

GeminiWorker 需要同時具備兩個能力：
1. **清除舊任務**（已排隊但尚未開始處理的 segment）
2. **中止當前任務**（正在跑的 `stream_gemini()` 迭代）

#### 為什麼不能用 Qt QueuedConnection 呼叫 flush_and_abort()

`stream_gemini()` 是一個阻塞的 HTTP 串流請求，執行時整個 QThread 的事件迴圈被佔用。若用 Signal 的 `QueuedConnection` 呼叫 `flush_and_abort()`，該呼叫會排到事件佇列裡，永遠等不到 `stream_gemini()` 結束後才執行——P1 中止就失效了。

**正確做法**：`flush_and_abort()` 從 GUI thread **直接呼叫**（非 Signal），利用 Python GIL 保護跨執行緒的 bool 寫入。`collections.deque` 本身的 `appendleft` / `clear` 在 CPython 下是執行緒安全的。

```python
# GeminiWorker 改造方向
from collections import deque
import threading

# deque 替代 queue.Queue：
#   - P3: deque.append(task)         → 排到尾端
#   - P2: deque.appendleft(task)     → 插到最前端
#   - P1: deque.clear() + append(task) → 清空後排入
_task_deque: deque = deque()
_abort_current: bool = False   # 跨執行緒旗標，GIL 保護下安全

def flush_and_abort(self) -> None:
    """P1 觸發時由 GUI thread 直接呼叫（不用 Signal），立即生效。"""
    self._task_deque.clear()        # 清空待處理任務
    self._abort_current = True      # 通知進行中的 stream_gemini() 提前退出
    logging.info("[GeminiWorker] Flushed deque and set abort flag (P1 event)")

@QtCore.Slot(float, float, object)
def process_segment(self, start_t: float, stop_t: float, data: object) -> None:
    """P3 用途：由 Signal 呼叫，任務排到尾端。"""
    self._task_deque.append((start_t, stop_t, data))
    if not self._busy:
        self._drain_deque()

def enqueue_front(self, start_t: float, stop_t: float, data: object) -> None:
    """P2 用途：由 GUI thread 直接呼叫，任務插到最前端。"""
    self._task_deque.appendleft((start_t, stop_t, data))
    if not self._busy:
        self._drain_deque()

def _drain_deque(self) -> None:
    """在 Worker QThread 內執行，持續消化直到 deque 清空。"""
    self._busy = True
    try:
        while self._task_deque:
            start_t, stop_t, data = self._task_deque.popleft()
            self._abort_current = False
            self._process_one(start_t, stop_t, data)
    finally:
        self._busy = False

def _process_one(self, start_t, stop_t, data) -> None:
    """實際呼叫 stream_gemini()，每次 yield 後檢查 _abort_current。"""
    for ev in stream_gemini(data):
        if self._abort_current:
            logging.info("[GeminiWorker] Aborted mid-stream %.2f-%.2f", start_t, stop_t)
            return
        if not priority_emitted and ev.priority is not None:
            self.signal_priority.emit(start_t, stop_t, ev.priority, bool(ev.should_speak))
            priority_emitted = True
        if not broadcast_emitted and ev.broadcast_text is not None:
            self.signal_broadcast.emit(start_t, stop_t, ev.to_dict())
            broadcast_emitted = True
```

**GUI 呼叫時序（P1 命中時）：**
```python
# on_segment_received() 中
if is_p1:
    interrupt_tts()                                        # 清 TTS 佇列（直接呼叫 core 函式）
    self._gemini_worker.flush_and_abort()                  # 直接呼叫，不用 Signal
    self._gemini_worker.enqueue_front(start_t, stop_t, data)  # 直接呼叫，插最前

# P2 命中時
elif is_p2:
    self._gemini_worker.enqueue_front(start_t, stop_t, data)  # 直接呼叫

# P3 命中時（一般路徑）
else:
    self._gemini_worker_signal.emit(start_t, stop_t, data)    # 走 Signal 佇列正常排
```

**P1 觸發後的狀態**：deque 清空、TTS 佇列清空、`_abort_current=True` 讓進行中的 stream 在下一個 yield 點退出，系統只剩 P1 這一個任務待處理。

## 4. MatchTracker 實作規格

### 4.1 位置與職責

新建 `src/miis_broadcast/core/match_tracker.py`，Singleton 模式，執行緒安全。

```python
class MatchTracker:
    """Python 側唯一真相來源。LLM 只看、不寫。"""
    red_score: int
    blue_score: int
    period: int
    last_event: str  # 最後一個 P1 事件描述

    def add_score(self, team: str) -> None  # thread-safe
    def get_state_string(self) -> str       # 供注入 Gemini prompt
    def reset(self) -> None
    def set_period(self, n: int) -> None
```

### 4.2 計分觸發時機（已確定）

**快軌不直接計分，由 Gemini 確認後觸發。**

流程：
1. 快軌掃描到 P1 關鍵字 → 觸發全線清除 + 優先送 Gemini
2. Gemini 分析完整語意，在 `signal_broadcast` 回傳 `action_label` 含 `"score"` 或 `"goal"`
3. GUI 的 `on_broadcast_received()` 收到後，呼叫 `MatchTracker.add_score(team)`

**為什麼不在快軌直接計分**：快軌只看關鍵字，無法辨識隊伍（jersey number → team 需要查表），也無法區分「進球成功」與「嘗試投籃」的描述。Gemini 有完整語意和 RAG 知識（球員所屬隊伍），是唯一能可靠判斷的節點。

`MatchTracker.add_score()` 的 `team` 參數來自 Gemini 回傳的 `action_label`，格式建議：`"score_red"` / `"score_blue"`，由 Gemini system prompt 約束輸出。

GUI 提供手動修正介面（+/- 按鈕）處理誤判。

### 4.3 注入 Gemini 的格式

在 `gemini_broadcaster.py` 的 `stream_gemini()` 中，擴充 prompt：

```
[Game context: {rag_data}]
[Match state: {match_tracker.get_state_string()}]
{livecc_visual}
```

`get_state_string()` 範例輸出：`"Red 3 : Blue 2, Q2, last event: jump shot"`

## 5. 事件驅動 KV 快取重置

### 5.1 現況

`LiveCCCameraWorker` 已有 `memory_reset_every=5` 時間驅動重置。

### 5.2 缺口

P1 事件（死球、進球）後應立即重置，避免 KV cache 帶著舊的動作記憶推論新的開球畫面。

### 5.3 修法

在 `LiveCCCameraWorker` 加一個 Slot：

```python
@QtCore.Slot()
def requestMemoryReset(self) -> None:
    """外部呼叫（P1 信號觸發），立即清空 KV Cache。"""
    self._state = {}
    logging.info("[LiveCCCameraWorker] Memory reset triggered by P1 event")
```

GUI 側：接收到 `signal_priority(P1)` → 連接 `liveCCCameraWorker.requestMemoryReset()`

### 10.2 Gemini 模型版本

`gemini_broadcaster.py:195` 目前使用的模型從 `configs/app.yml` 的 `gemini.model_name` 讀取，預設值 `"gemini-3.1-flash-lite-preview"`。任務開始前確認這是否為目標版本，或需換成延遲更低 / 語意更強的版本。

### 10.3 requestMemoryReset() 的連線方式

任務 6 的 `requestMemoryReset()` Slot **必須用 Signal 呼叫（QueuedConnection）**，不能直接呼叫。直接從 GUI thread 呼叫會在 Worker thread 正在執行推論時競爭 `self._state`，造成不可預期的行為。連接寫法：
```python
self.signal_p1_event.connect(
    self._livecc_camera_worker.requestMemoryReset,
    QtCore.Qt.QueuedConnection
)
```
